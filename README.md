## Задание 1. СУБД

### 1.1. Бюджетирование проектов и финансовые отчеты
* **Выбор СУБД:** **Реляционная СУБД (RDBMS)** — например, **PostgreSQL** или **Oracle Database**.
* **Обоснование:** Финансовые аналитические отчеты, бюджетирование и оценка рисков требуют строгой структуры данных, поддержки ACID-транзакций (чтобы исключить рассинхронизацию финансов) и поддержки сложных аналитических SQL-запросов (агрегаты, JOIN).
* **1.1.\* Дополнительный вопрос:** Для ускорения процессов хеширования или криптографических операций можно использовать **Hardware API / Crypto Acceleration API** (например, **OpenSSL EVP API**, интерфейсы **PKCS#11** для работы с аппаратными модулями HSM или инструкции процессора **Intel SHA Extensions / AES-NI**). Также на уровне БД применяется кеширование результатов хеширования через **In-Memory Caching API** (Redis/Memcached).

### 1.2. Лендинги и CRM
* **Выбор СУБД:**
  * **Для лендингов:** **Документоориентированная NoSQL СУБД (MongoDB)** или **Ключ-Значение (Redis)**. Они обеспечивают высокую скорость записи и гибкую схему для обработки разрозненных веб-форм и метрик.
  * **Для CRM:** **Реляционная СУБД (PostgreSQL)** или **Документоориентированная СУБД (MongoDB)** с хорошей поддержкой индексов.
* **Обоснование:** Данные с лендингов поступают в полуструктурированном виде (разный набор полей у разных лидов), поэтому гибкая schema-less архитектура NoSQL идеальна. CRM требует быстрого поиска по лидам, контактам и истории сделок.
* **1.2.\* Дополнительный вопрос:** **Да, можно.** Отлично подойдет **PostgreSQL** с использованием типа данных **JSONB** и GIN-индексов. Это позволяет хранить неструктурированные данные лидов с лендингов в формате JSON, сохраняя высокую скорость NoSQL, но при этом иметь надежную реляционную базу для сущностей CRM (сделки, менеджеры, статусы).

### 1.3. База знаний по корпоративным нормам
* **Выбор СУБД:** **Документоориентированная NoSQL СУБД (MongoDB, CouchDB)** или **Иерархическая/Графовая СУБД**. В качестве практического инженерного решения — движки корпоративных вики (например, Confluence / Wiki-системы на базе PostgreSQL или MySQL).
* **Обоснование:** Корпоративные нормы, регламенты и обучающие материалы представляют собой древовидную или иерархическую структуру документов (разделы, статьи, регламенты) с текстовым поиском.
* **1.3.\* Дополнительный вопрос:** **Да, можно.** Можно использовать **PostgreSQL**, создав таблицу с рекурсивными связями (Parent ID для древовидной структуры статей) и включив полнотекстовый поиск (**Full-Text Search / tsvector**). Также документы можно хранить в виде JSONB-структур.

### 1.4. Логистика и формирование маршрутов
* **Выбор СУБД:** **Графовая СУБД (Graph DBMS)** — например, **Neo4j** или **ArangoDB**.
* **Обоснование:** Логистические точки, объекты строительства и курьерские маршруты идеально моделируются в виде графа (узлы — склады/объекты, рёбра — дороги/расстояния). Графовые СУБД нативно оптимизированы под обход графов и поиск кратчайших путей (алгоритмы Дейкстры, A*).
* **1.4.\* Дополнительный вопрос:** **Да, можно.** Отдел закупок можно подключить к той же СУБД, так как поставщики и номенклатура материалов также образуют граф связей («Поставщик» → «Материал» → «Объект доставки»). Однако архитектурно лучше выделить отдельную **RDBMS (PostgreSQL)** для учета складов и финансов закупок, связав её с графовой СУБД логистов через **API / Integration Event Bus (Kafka/RabbitMQ)**.

### 1.5.* Единая СУБД для всех задач
* **Ответ:** **Да, можно.**
* **Выбор СУБД:** **Мультимодельная СУБД (PostgreSQL)** или **ArangoDB**.
* **Обоснование:** **PostgreSQL** благодаря расширениям покрывает все нужные модели:
  1. Реляционные таблицы для финансов и бюджетирования (ACID).
  2. `JSONB` для лидов, CRM и документов базы знаний.
  3. Модуль `pgRouting` и графовое расширение `Apache AGE` для решения логистических задач обхода графов.
  4. Встроенный полнотекстовый поиск для базы знаний.

## Задание 2. Транзакции

### 2.1. Шаги успешной транзакции пополнения баланса телефона
Пополнение счета телефона через мобильный банк/терминал включает 6 ключевых шагов:

1. **Инициация и проверка данных:** Пользователь вводит номер телефона и сумму. Система проверяет корректность формата номера и наличие средств на карте/счете.
2. **Блокировка средств (Hold/Begin Transaction):** СУБД банка стартует транзакцию и временно резервирует (замораживает) необходимую сумму на счете списания.
3. **Запрос к платежному шлюзу (Processing):** Запрос передается процессинговому центру для авторизации операции в платежной системе (Visa/Mastercard/MIR/СБП).
4. **Перевод средств биллингу оператора:** Процессинг подтверждает списание средств и отправляет уведомление в биллинговую систему мобильного оператора.
5. **Зачисление на баланс:** Биллинговая система оператора выполняет транзакцию по увеличению баланса абонента.
6. **Завершение (Commit Transaction):** Банковская СУБД фиксирует транзакцию (`COMMIT`), окончательно списывает заблокированные средства и возвращает пользователю статус «Успешно» с выдачей чека.

### 2.1.* Транзакция через «Автоплатеж»
При автоплатеже цепочка событий меняется на старте:

1. **Триггер события (Cron / Webhook / Threshold):** Планировщик задач (Scheduler) или событие от оператора (баланс опустился ниже порога X) генерирует фоновую задачу.
2. **Проверка условий подписки:** Система автоплатежей проверяет лимиты, активность карты и расписание.
3. **Фоновая инициация транзакции:** Сервис банка создаёт транзакцию списания без участия интерфейса пользователя.
4. **Авторизация и списание:** Происходит списание денег с привязанного счёта в банке (с использованием токена/рекуррентного платежа).
5. **Зачисление у оператора:** Передача средств в биллинг оператора и пополнение баланса.
6. **Уведомление пользователя (Push/SMS):** Завершение транзакции и отправка асинхронного Push-уведомления/SMS абоненту о совершенном автоматическом списании.

## Задание 3. SQL vs NoSQL

### 3.1. Пять преимуществ SQL-систем над NoSQL
1. **Поддержка ACID-транзакций:** Гарантия полной целостности, атомарности и непротиворечивости данных, что критично для банковских и финансовых систем.
2. **Стандартизированный язык запросов (ANSI SQL):** Единый стандарт декларативного языка, позволяющий легко строить сложные аналитические выборки любой глубины.
3. **Строгая схема данных (Data Integrity):** Защита от невалидных или мусорных данных на уровне самой СУБД (Primary Key, Foreign Key, CHECK, NOT NULL).
4. **Сложные соединения (JOINs):** Высокооптимизированный механизм объединения множества связанных таблиц в рамках одного запроса.
5. **Зрелость экосистемы и инструментария:** Десятилетия развития, огромное количество готовых ORM, админок, утилит бэкапа и квалифицированных специалистов.

### 3.1.* Преимущества NewSQL систем
NewSQL сочетает строгий ACID и SQL-интерфейс классических БД с горизонтальным масштабированием и отказоустойчивостью NoSQL (например, CockroachDB, Google Spanner, YugabyteDB).

* **Преимущества перед SQL:**
  1. Нативное горизонтальное шардирование и масштабирование «из коробки» без усложнения архитектуры.
  2. Высокая доступность и устойчивость к падению ЦОД (Multi-DC / Geo-replication) на уровне встроенных консенсус-алгоритмов (Raft/Paxos).
* **Преимущества перед NoSQL:**
  1. Полноценная поддержка распределенных ACID-транзакций без потери производительности.
  2. Сохранение привычного SQL-синтаксиса и строгой типизации данных.

## Задание 4. Кластеры (1000 машин)

### Критерий выбора СУБД и модель распределенных вычислений

1. **Критерий выбора СУБД:**
   * **Горизонтальная масштабируемость (Horizontal Scalability / Sharding):** Способность системы линейно увеличивать производительность при добавлении новых узлов в кластер.
   * **Соответствие CAP-теореме:** В зависимости от приоритета задачи (Availability vs Consistency) выбирается CP или AP система.
   * **Поддержка массово-параллельной обработки (MPP - Massively Parallel Processing):** Способность распределять один вычислительный запрос между сотнями серверов одновременно.

2. **Модель распределенных вычислений:**
   * Лучше всего справится модель **MapReduce** (или её современные реализации в виде **Distributed Dataflow / Apache Spark / Hadoop**).

3. **Почему именно эта модель:**
   * **Разделяй и властвуй:** Задача разбивается на тысячи мелких подзадач (`Map`), которые параллельно выполняются на 1000 машинах локально над их фрагментом данных, после чего результаты агрегируются (`Reduce`).
   * **Устойчивость к сбоям (Fault Tolerance):** На кластере из 1000 машин сбои отдельных серверов происходят постоянно. Модели типа MapReduce/Spark автоматически переназначают упавшие задачи на другие здоровые узлы без перезапуска всей вычислительной задачи.
   * **Локальность данных (Data Locality):** Вычисления отправляются к местам хранения данных, что минимизирует паразитный сетевой трафик между 1000 серверами.
